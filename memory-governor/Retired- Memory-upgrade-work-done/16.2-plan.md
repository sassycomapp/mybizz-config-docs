## A. Schema-pack repair — FINDING: `gbrain-engineer` is a dead end for the call graph

1. **Packs available to gbrain 0.46.1.0** (`gbrain schema list`):
   - Bundled: `gbrain-base`, `gbrain-recommended`, `gbrain-creator`,
     `gbrain-investor`, `gbrain-engineer`, `gbrain-everything`, `gbrain-base-v2`.
   - Installed (`~/.gbrain/schema-packs/`): **`gbrain-everything` only**.
2. **`gbrain-engineer`** is bundled but **not installed**; it is compatible/supported (ships with the release).
3. **Manifest** (`gbrain schema show gbrain-engineer`): `extends: gbrain-base`,
   adds exactly **1 page type** (`learning :: annotation`), **0 link verbs**,
   and "reuses gbrain-base's `code` page type unchanged". It does **not** declare
   code-symbol, call-edge, or caller/callee extraction.
4. **`code` page type** (`gbrain schema explain code`): `primitive: media`,
   **`extractable: false`** — inherited from `gbrain-base` into every bundled pack.
5. **Conclusion:** no bundled or installed pack extracts code-symbol edges.
   Switching to `gbrain-engineer` (or any bundled pack) will **not** enable
   `code-callers`/`code-callees`. This corrects the Package 16.1 hypothesis.
   Enabling the call graph requires a **code-aware schema pack that is not in
   the bundled set** — per this task, do **not** install an unverified external
   pack, so this repair is **deferred**, not silently failed.
6. **Reversibility:** `gbrain schema downgrade [--to <pack>]` restores the prior
   active pack (activation is reversible).
7. **Blast radius of a pack switch:** affects only **page-type assignment** for
   future processing (plus optional re-typing via `gbrain schema sync --apply`).
   Existing **pages, chunks, embeddings, and source registrations are untouched**
   (they live in the DB independent of the pack).
8. **Commands:** `gbrain schema list` / `show <pack>` / `use <pack>` /
   `downgrade [--to <pack>]` / `validate` / `lint` / `stats` / `explain <type>`.

## C. Sync repair — FINDING: 3 sources are sync-stale; per-source sync is the fix

1. **Sync-stale sources** (`doctor sync_freshness`): `dev-root-hub`,
   `mb4ecom-project-library`, `mb5pdlf-project-library` (last synced ~5d ago).
2. **Why:** incremental sync has not run for them in 5 days (no scheduled
   sync/autopilot pass). Their paths are `/mnt/c/dev/dev-root`,
   `/mnt/c/dev/dev-mb4ecom/mb4ecom-project-library`,
   `/mnt/c/dev/dev-mb5pdlf/mb5pdlf-project-library`.
3. **Least-broad command:** `gbrain sync --source <id>` per source (3 runs), or
   `gbrain sync --all --parallel 4 --workers 4 --skip-failed` (doctor-recommended).
4. **Dry-run exists:** `--dry-run` ("show what would be synced without writing");
   also `--no-pull` (skip internal git pull) and `--json`.
5. **Effect:** `gbrain sync` writes to the **GBrain DB** (import + embed) and, by
   default, performs an internal **`git pull` of each source repo**. It does
   **not** touch local guidance files (`agents.md`); that is a separate manual step.

## D. Cycle repair — FINDING: full dream does NOT stamp per-source; scope it

1. **Exact command:** `gbrain dream --source <id>` (scopes the cycle and stamps
   `last_full_cycle_at` for that source) or `gbrain dream` (brain-global, no
   per-source stamp). `--dry-run` and `--json` are supported.
2. **Root cause of remaining staleness:** `dream.ts` threads `sourceId` into the
   cycle so `last_full_cycle_at` is written per-source **only when `--source` is
   passed**. The full `gbrain dream` (no `--source`) in Package 16.1 therefore
   did **not** clear `cycle_freshness` for `default`, `dev-makepdlf`,
   `dev-root-hub`, `mb-3-cs-project-library`.
3. **Code-source processing order:** the call graph is blocked by the missing
   code-aware pack (Section A), not by cycle ordering — so there is no
   code-source-processing-order prerequisite to satisfy with the current pack set.
4. **Minimum rerun set:** 4 scoped cycles — `default`, `dev-makepdlf`,
   `dev-root-hub`, `mb-3-cs-project-library` (`mb-3-cs-code` already stamped in 16.1).
