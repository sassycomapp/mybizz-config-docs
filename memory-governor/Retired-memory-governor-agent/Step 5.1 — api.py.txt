Step 5.1 — api.py (Part 1 of several — submission endpoint)

Given api.py needs to expose eleven endpoints from Architecture §3.2, I'm building it the same way the schema migrations were built — one piece at a time, verified before the next, rather than one large heredoc. This turn: the credential-authentication dependency and the most complex, most important endpoint — POST /memory/candidate, the full submission pipeline. Later turns cover the read endpoints, review/supersede/quarantine, and project/policy management.

Several genuine design decisions surfaced writing this — none specified by either foundation document, all flagged rather than silently assumed:

How a credential is presented over HTTP is undefined by any spec. Choosing a custom header, X-Governor-Credential, over Authorization: Bearer — simple, unambiguous, and doesn't imply OAuth semantics this system doesn't have.
The request body needs a narrower shape than the full GovernedMemoryCandidate model. Several fields must be server-computed, never caller-supplied: writer_identity and lineage_hash (Step 3.1's guarantee), timestamps (server sets created_at/updated_at at submission time), policy (entirely computed by decide_path()), and status (forced by initialize_candidate()). I'm introducing a separate CandidateSubmissionRequest Pydantic model in api.py itself — an API-layer shape, not a domain model, so it doesn't belong in models.py — that structurally excludes all of these, the same way build_provenance() structurally excludes writer_identity.
memory_id is optional in the request; the server generates a UUID4 if omitted. Not specified anywhere — a reasonable default that still lets a caller (e.g. GBrain dreaming, if it wants deterministic IDs) supply its own.
Scope.owning_project is derived from the request's top-level owning_project, not accepted as a separate field — avoids a caller supplying two different values that silently disagree.
HTTP 201 Created for every successful submission, regardless of which decision_path it lands on (even quarantine/reject) — a resource genuinely was created; the response body's status field tells the caller what actually happened.

Step 5.1 Part 4 — review endpoints (GET /memory/review-queue, POST /memory/{memory_id}/review)

One real, honest gap to flag before the code — this one isn't fixable the way the last two were; it's a genuine limitation to carry forward, not silently paper over.

There is no verified "reviewer identity" concept anywhere in this system. Step 3.1 built a structural guarantee for writer_identity — it's cryptographically tied to a presented credential, impossible to spoof. reviewer has no equivalent. Step 0.3 only provisioned two credentials, gbrain_dreaming and manual_submission — neither represents "a specific human reviewer." So POST /memory/{memory_id}/review can only gate access the same way every other endpoint does (any known credential), while reviewer itself stays exactly what it's been in every test so far: a free-text string, self-reported in the request body, with nothing verifying it. This is a real, structural difference in trust level between provenance.writer_identity (Step 3.1, unforgeable) and audit_log.reviewer (self-reported, forgeable) — worth naming plainly rather than letting the parallel naming imply a parallel guarantee that doesn't exist. If this ever needs to be closed, it requires a genuinely new mechanism (per-human credentials, not per-writer-role ones) — out of scope for this step.

Step 5.1 Part 8 (final) — POST /memory/policy

Two real design questions to flag before code — both genuinely underspecified by either foundation document, not silently resolved.

1. What does "confidence" mean for a policy proposal? Every other candidate's confidence score reflects genuine uncertainty about a fact. A policy proposal has no equivalent concept — but GovernedMemoryCandidate requires the field. Resolving this cleanly: since memory_type="policy" is in HIGH_RISK_TYPES, decide_path()'s own ordering (Step 1.3) checks risk level before confidence and unconditionally routes any high-risk candidate to needs_review regardless of score. So the confidence value is structurally inert here — it cannot change the outcome. Using a fixed placeholder (1.0, method="rule_based") rather than inventing a fake uncertainty measure that doesn't correspond to anything real.

2. Policy is governor-wide; the schema is project-scoped. Every candidate requires owning_project (a real FK to projects). Policy thresholds conceptually apply to the whole governor, not one project — but there's no "global" concept anywhere in this schema, and building one now would be exactly the kind of premature complexity the credo warns against. Pragmatic, explicitly flagged choice: require the caller to specify a real, already-registered owning_project for audit/attribution purposes, same as any other candidate.
