Step 3.2 — audit.py

One real, load-bearing gap surfaced while designing this step — flagging it before any code, same discipline as every step so far.

The schema has no actual audit history table. Looking back at what's already built: state_machine.py's apply_decision() already writes to candidate.audit — but that's a single JSONB object on the memory_candidates row itself (decision_by, decision_at, decision_reason, reviewer), and every call to apply_decision() overwrites it. There is currently no way to see that a candidate was quarantined on Monday and then promoted on Thursday — only the most recent decision survives. Architecture §9 describes audit.py's job as "append immutable decision records" — that word "append" cannot be satisfied by a column that gets replaced on every write. This is a genuine gap in the schema from Step 2.1, only surfacing now because this is the first step that actually needs a real history.

Fix: a new table, audit_log, append-only, one row per decision, added via a new migration. audit.py owns writing to it. Consistent with the established dependency boundary from Step 1.2/2.3: state_machine.py stays storage-independent — it still only returns a MemoryDecision object, and does not call audit.py itself. The caller (Phase 5's api.py, eventually) is responsible for calling both state_machine.apply_decision() and audit.append_audit_entry() together. audit.py depends on storage.py and models.py only, matching Architecture §9's stated dependency order exactly.
