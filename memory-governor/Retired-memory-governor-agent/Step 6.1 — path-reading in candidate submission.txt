Step 6.1 — Path-reading in candidate submission

Before any code — this step has more real design forks than most, and I want to lay them out and get your direction before building anything, same discipline as every consequential decision so far.

1. How does the server decide "this is a path submission" vs. "this is inline content"?
Current CandidateSubmissionRequest.content is required. To support path-based ingestion, content needs to become optional. Proposed rule: if content is omitted (or empty) and source_ref resolves to a real, readable file or directory on disk, treat it as a path submission and read from it. If content is provided, use it directly — never silently re-interpret source_ref as a path in that case, even if it happens to look like one. This matches Architecture §5's wording exactly ("when content.text is absent and source_ref resolves to a readable path").

2. Folder submission produces multiple candidates from one API call — this changes the response shape.
Every endpoint in this codebase so far returns one object for one operation. A folder submission is architecturally different: one request, potentially many candidates, each independently going through decide_path() and potentially landing on a different outcome (one auto-promotes, another gets quarantined, a third needs review). The response needs to become a list of per-file results, not a single dict — a real, visible API shape change for this one endpoint. Proposing: single-file submissions still return today's single-object shape (no behavior change for the common case); folder submissions return {"submitted": [ ...one result object per file... ]}. Confirm you're comfortable with this, or would prefer single-file submission's response shape to change too, for consistency.

3. Security — this is a real, not theoretical, concern worth naming plainly.
This endpoint would let an authenticated caller ask the server to read any file path the server process itself has read access to. In this project's actual context — solo developer, local-only WSL environment, the credential is already a strong per-writer secret from Step 0.3 — the realistic threat model is narrow. But "narrow" isn't "none": a caller with a valid credential could currently read ~/.env, SSH keys, or anything else the dev-p user can access, not just intended project documents. Proposing a minimal, explicit allowlist of permitted root directories (e.g. /mnt/c/dev/, /home/dev-p/memory-governor/ itself for testing) rather than an unrestricted filesystem read — simple to implement, closes the obvious risk, doesn't require inventing a heavier permissions system. Confirm this is the right level of caution for this project, or tell me if you want it even more restrictive (e.g., paths must be inside the specific owning_project's known location) or are comfortable with less.

4. Binary/unreadable files and nonexistent paths need defined behavior, not silent failure.
Proposing: a source_ref that doesn't exist at all → 404. A file that exists but can't be decoded as UTF-8 text (e.g., accidentally pointing at a binary file) → skipped with a per-file error noted in the response, not a fatal failure for the whole batch — so one bad file in a folder doesn't block every other file from being ingested.

My recommendation on all four, if you'd rather I just decide: proceed as proposed above — optional content with source_ref-as-path fallback, list-shaped response only for folder submissions, a small explicit directory allowlist, and per-file error isolation for unreadable files. This is the narrowest, most defensible design that satisfies Architecture §5 without inventing anything beyond what's actually needed.

def submit_candidate(
    req: CandidateSubmissionRequest,
    presented_credential: str = Depends(get_presented_credential),
):
    """
    Step 6.1: if req.content is omitted, source_ref is resolved as a
    filesystem path (Architecture §5). A single file submits exactly as
    before (same single-object response shape, no change for existing
    callers). A directory submits ONE CANDIDATE PER FILE -- a genuine,
    visible response-shape change for this case only: returns
    {"submitted": [...]}, one result entry per file, each independently
    routed through the full decide_path() pipeline. A file that fails to
    decode as text is skipped with its own error entry, not a fatal
    failure for the whole batch.
    """
    if req.content is None:
        try:
            files = resolve_source_ref_to_files(req.source_ref)
        except FileNotFoundError as exc:
            raise HTTPException(status_code=404, detail=str(exc))
        except PermissionError as exc:
            raise HTTPException(status_code=403, detail=str(exc))

        if len(files) == 1 and Path(req.source_ref).is_file():
            text = _read_text_file(files[0])
            if text is None:
                raise HTTPException(status_code=400, detail=f"'{req.source_ref}' could not be decoded as text")
            req.content = Content(text=text)
            return _submit_single_candidate(req, presented_credential)

        results = []
        for file_path in files:
            text = _read_text_file(file_path)
            file_req = req.model_copy(deep=True)
            file_req.source_ref = str(file_path)
            if text is None:
                results.append({"source_ref": str(file_path), "error": "could not be decoded as text"})
                continue
            file_req.content = Content(text=text)
            try:
                result = _submit_single_candidate(file_req, presented_credential)
                result["source_ref"] = str(file_path)
                results.append(result)
            except HTTPException as exc:
                results.append({"source_ref": str(file_path), "error": exc.detail, "status_code": exc.status_code})
        return {"submitted": results}

    return _submit_single_candidate(req, presented_credential)
