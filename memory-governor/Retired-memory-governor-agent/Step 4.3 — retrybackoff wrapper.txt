Step 4.3 — Retry/backoff wrapper

One real, load-bearing gap surfaced designing this step — flagging it before any code, same discipline as always.

The current schema can't actually represent "stop retrying, this has permanently failed." memory_events has attempt_count and last_error (from Step 2.1), but nothing that distinguishes "still pending, will retry" from "exhausted its retries, needs human attention, never touch again." Without an explicit signal, run_polling_pass() would just keep picking a failed event back up on every future pass forever — directly contradicting Architecture §8.3's own requirement: "stops retrying automatically... surfaced to the developer... rather than retried silently forever."

Fix: two new columns, added via a new migration:

permanently_failed BOOLEAN NOT NULL DEFAULT FALSE — the explicit stop signal.
next_retry_after TIMESTAMPTZ — when this event becomes eligible for its next attempt. This is also how real exponential backoff gets implemented without blocking the worker with time.sleep() — a sleep inside process_event() would stall every other pending event too, defeating the whole point of Phase 4's non-blocking design. Instead, a failed attempt schedules a future eligibility time, and run_polling_pass()'s own query simply skips anything not yet eligible — the existing polling cadence is the backoff mechanism, reusing infrastructure already built rather than adding a second one.
