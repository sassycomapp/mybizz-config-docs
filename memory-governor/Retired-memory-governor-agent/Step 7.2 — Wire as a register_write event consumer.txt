Step 7.2 — Wire as a register_write event consumer

Before writing any code, I found a real conflict between the Workflow's literal wording and the actual, already-tested architecture, and I want to flag it precisely rather than implement something that contradicts a deliberately-built boundary.

The Workflow says the register_write event should be inserted "in state_machine.py's apply_decision()." But state_machine.py was deliberately built storage-independent back in Step 1.2 — it has zero database dependency, proven by its own enforcement test (test_status_field_never_assigned_outside_state_machine) and confirmed again in Step 2.3's design note ("state_machine.py's whole point is staying storage-independent"). Inserting an outbox event there would mean giving it a database connection, breaking that boundary for the first time in this codebase. I'm not doing that — the Workflow's wording here doesn't match the architecture that was actually built and tested, and the architecture should win.

The real, deeper issue underneath that: emitting a register_write event on promotion means firing two events from one status change — whatever the endpoint's own event already is (candidate_created, review_resolved, etc.) plus register_write, both needing to land in the same atomic transaction as the status update. outbox.py's atomic functions currently only support inserting one event per call. This isn't a workaround-able detail — it's a genuine gap that Phase 12 (GBrain writes) will hit in exactly the same shape, so solving it generically now, once, is the right move rather than patching around it twice.

The fix: extend outbox.py's two atomic functions with an optional additional_events parameter, reusing the low-level emit_event(cur, ...) primitive that already exists and already takes an open cursor without committing — no new mechanism, no new table, just calling something already built one more time before the single commit.
