Step 4.1 — outbox.py

One real architectural gap surfaced designing this step — flagging it before code, same discipline as always.

Architecture §4 requires the event insert to happen "in the same transaction as the state change itself." Nothing built so far can actually do that. Checking the existing code: storage.update_candidate() opens its own connection, does its own UPDATE, and calls conn.commit() internally — the transaction is already closed by the time control returns to the caller. There is no way for a second, separate call (an event insert) to join a transaction that's already committed. "Insert the event in the same transaction as the state change" is a real requirement Architecture §4 states outright — it can't be satisfied by calling storage.update_candidate() followed by a separate event-insert call, no matter how quickly they run one after another.

Fix: outbox.py does not call storage.update_candidate()/storage.insert_candidate() at all. It provides its own atomic, composed functions that open exactly one connection, perform the candidate write and the event write together, and commit once. This reuses storage.py's internal _serialize() (same package, deliberately reused rather than duplicated) but does not go through storage.py's existing public functions, since those functions' own internal commit is precisely the thing that breaks atomicity here. storage.insert_candidate()/update_candidate() remain correct and useful on their own — for read-modify-write flows where atomicity with an event isn't needed — this is an additional, atomic path alongside them, not a replacement.

One more design choice, flagged: NOTIFY payloads can't use normal parameter binding in raw SQL — Postgres's NOTIFY channel, 'payload' syntax only accepts a string literal, not a bind parameter. Using pg_notify(channel, payload) instead, which is a real function and does accept normal parameterized calls — the standard, safe way to do this.
