Step 16.1 — Establish the direct-operation discipline for GBrain dreaming
Memory Governor Agent — Phase 16 (Cutover)
================================================================================

ORIGINAL WORDING (Workflow v1.3, now superseded)

Step 16.1 — Wire the real GBrain-dreaming writer
- Action: point the actual GBrain dreaming process at the governor using
  its Step 0.3 credential, in place of writing directly to GBrain.

This assumed GBrain's own "dream" process could be configured or redirected
to route its writes through the memory governor's API, the same way the
other three writers (manual submission, self-healing, PDLF step-sync) do.


--------------------------------------------------------------------------------
WHY THIS NEEDED REVISING
--------------------------------------------------------------------------------

Before writing any code against this step, its central assumption was
investigated directly rather than taken on faith. The investigation was
exhaustive, not a single check:

1. gbrain remember --help and the full gbrain --help output were read in
   full. No --source flag or redirect mechanism was documented for any
   write verb.

2. gbrain --tools-json was fetched and inspected directly -- the real,
   complete MCP tool schema, not assumed from documentation. "dream" does
   not appear in it at all, confirming it is a standalone CLI maintenance
   process, not a callable protocol verb with configurable parameters.

3. gbrain config show was run and inspected directly. Its entire
   configuration surface is GBrain's own internal engine (database,
   embedding model, chat model, API keys) -- nothing resembling a
   redirect, output-target, or governor-endpoint setting exists anywhere
   in it.

4. gbrain dream --dry-run --json was run and its real, complete output
   inspected. Dream runs as a sequence of roughly twenty independently
   reporting phases (extract_facts, extract_atoms, synthesize_concepts,
   consolidate, propose_takes, grade_takes, embed, purge, and others).
   Several phases write directly to GBrain's own database through its own
   internal engine, with no exposed interception point anywhere in the
   sequence.

Conclusion, confirmed rather than assumed: there is no supported way,
through any documented configuration surface, to route GBrain's own
"dream" writes through the memory governor's API.

Two real alternatives were considered and explicitly rejected:

  a) Forking GBrain's own source to intercept its internal writes --
     rejected for the same reasoning already applied elsewhere in this
     project when GBrain's `remember` verb itself was under consideration
     for a custom fork: it would create a permanent obligation to
     re-merge against GBrain's own ongoing releases, forever, for a
     problem that may be solvable another way.

  b) Building a proxy/interception layer sitting between dream's internal
     logic and its own database -- a fundamentally different, much larger
     kind of engineering task than anything else in this project, closer
     to reverse-engineering a third-party tool's internals than governing
     writes at a real API boundary.

Neither was adopted.


--------------------------------------------------------------------------------
THE REAL, WORKING ALTERNATIVE -- CONFIRMED, NOT ASSUMED
--------------------------------------------------------------------------------

Direct investigation of GBrain's actual behavior, plus independent
third-party review, together produced a genuine, working discipline for
this one writer.

Confirmed directly:

- A dry run writes nothing at all. Every phase in a --dry-run invocation
  reports "dry_run": true and produces no real content. A dry run cannot
  serve as a review step, only as a scope/cost preview.

- gbrain eval suspected-contradictions is a real, separate, purpose-built
  tool. Its own MCP tool description (find_contradictions) states plainly
  it "reads the cached run row -- does NOT trigger a new probe; users run
  `gbrain eval suspected-contradictions` for that." It does not run
  automatically as part of dream's own cycle -- confirmed directly against
  the real dry-run phase list, in which it never appears.

- "Takes" (AI-generated predictions/opinions with a stated confidence,
  later graded for accuracy against a resolved outcome) were confirmed,
  via the real takes_list/takes_scorecard/takes_calibration tool schemas,
  to be a feature built for a different use case entirely (the original
  VC-dealflow forecasting use case GBrain was built around). Zero takes
  exist in this brain, and none are expected to going forward given this
  project's actual use case. Not a gap -- genuinely not applicable here.

Confirmed via independent, third-party public review (not GBrain's own
marketing material): GBrain's own stated design assumption is that the
operator reviews its output personally. One independent review states
directly: dream cycle "does not fact-check the content or confirm the
knowledge is accurate or complete." A separate comparison piece notes
GBrain is single-operator by design, self-hosted only, and that for
anyone wanting a system where "memory writes don't need text-editor
review, it's a mismatch." The gap this step investigates is not a hidden
flaw -- it is GBrain's own documented operating assumption.


--------------------------------------------------------------------------------
THE ADOPTED DISCIPLINE (Step 16.1's actual resolution)
--------------------------------------------------------------------------------

Formally adopted as the accepted, documented governance mechanism for
this one writer -- the one deliberate, honestly-recorded exception to
"every writer's output is governed through the same API":

  1. Run `gbrain dream` for real -- not --dry-run, which writes nothing
     and cannot serve as a review step.

  2. Run `gbrain eval suspected-contradictions` immediately afterward --
     confirmed NOT automatic; must be explicitly invoked every time.

  3. Review the findings. High-severity contradictions get a real look;
     the rest can generally be trusted.

Agreed to run as part of ordinary per-step PDLF housekeeping, immediately
after whichever governed memory-write sequence has already run for that
step (manual submission / PDLF step completion / self-healing / policy
proposal) -- not deferred, not batched, run every time, on the same
"small frequent batches beat large deferred ones" principle already
applied to the five-point due diligence process.
