Step 4.2 — worker.py

Two real design points to flag before code — one an honest limitation of what's actually being built here, one a genuine correctness detail Architecture §4 doesn't spell out.

1. LISTEN/NOTIFY timing gap — worth understanding, not a bug. A connection only receives a NOTIFY if it was already LISTENing on that channel before the notifying transaction committed. If the worker's listen connection isn't open yet (or briefly disconnected) when an event fires, that specific notification is simply gone — Postgres doesn't queue it for a late listener. This is exactly why the polling fallback in Architecture §4 isn't a decorative afterthought — it's the actual correctness backstop. Design consequence: listen_loop() treats every wake-up — whether triggered by a real NOTIFY or by the poll timeout elapsing with nothing received — identically: run a full polling pass over everything currently unprocessed. There is deliberately only one code path that actually processes events (run_polling_pass()), not two that could silently drift apart.

2. An honest interim limitation, not silently accepted. process_event() doesn't catch exceptions from its handler. Right now every handler is a no-op, so this can't actually fail — but it means if a real handler (added in later phases) ever raises, that one event stays unprocessed and the current polling pass stops there, never reaching later pending events in the same batch. Step 4.3's retry/backoff wrapper is explicitly where this gets fixed with proper per-event isolation. Flagging now so it's understood as a known, temporary gap in this step's scope, not an oversight.

Testability note: a real deployment calls listen_loop() with no bounds and it runs forever. For anything to be verifiable in a live test or a test suite, it needs a stop condition — stop_after_seconds/stop_after_iterations parameters, unused in production, essential for proving this actually works.
