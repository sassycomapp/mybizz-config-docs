Step 3.1 — provenance.py

Per Architecture §9, this module owns "credential → writer_identity resolution; lineage utilities, source validation, supersession tracking, provenance-chain reconstruction." Per Scope Doc §11, the concrete guarantee this closes: writer_identity must never be self-reported — it's derived from which credential authenticated the request.

One honest design point up front, same discipline as every module so far: Pydantic's Provenance model itself cannot be made to physically forbid an arbitrary writer_identity string — it's just a typed field, and nothing stops someone from constructing Provenance(writer_identity="anyone") directly in Python. What this module can do, and does, is provide the single sanctioned constructor — build_provenance() — whose function signature does not accept writer_identity as a parameter at all. It only accepts a presented_credential, and derives writer_identity from that via lookup, with no path through this function for a caller to override it. The real enforcement is procedural: Phase 5's api.py must call build_provenance(), never construct Provenance directly from request data. I'm flagging this now so it's understood as the actual shape of the guarantee, not glossed over as an absolute technical impossibility it isn't.

Two smaller things, also flagged rather than silently decided:

Credential values are read from environment variables at call time, never hardcoded — reusing exactly the two credentials provisioned in Step 0.3 (MEMORY_GOVERNOR_WRITER_GBRAIN_DREAMING, MEMORY_GOVERNOR_WRITER_MANUAL_SUBMISSION).
lineage_hash computation is genuinely underspecified by both foundation documents — neither says what should be hashed or how. I'm implementing a defensible default (SHA-256 of content.text + provenance.source_ref, canonically ordered) and flagging it as a design choice open to revision, not a settled spec requirement.
