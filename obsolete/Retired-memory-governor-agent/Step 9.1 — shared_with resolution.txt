Confirmed — credentials resolve to a writer identity (gbrain_dreaming, manual_submission, pdlf_step_sync), never a project identity, and a single writer credential is shared across every project. There's no existing mechanism anywhere that identifies which project is asking to read something. Deciding this now rather than asking, per your standing instruction.

Design, decided:

An explicit requesting_project query parameter on the read endpoints — not inferred from the credential, since credentials are per-writer-type, not per-project, and building a whole new per-project reader-credential system would be exactly the unjustified complexity the credo rules out for a solo-developer tool with no adversarial multi-tenant threat model.
Backward-compatible by construction, not by exception: when requesting_project isn't supplied, behavior is byte-for-byte identical to today — this is purely additive capability, activated only when a caller identifies itself. No existing test should need to change.
A candidate is visible to a requesting project when: it's their own (owning_project match), or it's shared_all, or it's shared_specific and they're explicitly listed in shared_with.
GET /memory/{memory_id} needs the identical fix, not just the list endpoint. Right now direct-by-ID fetch has zero visibility awareness at all — any caller can read any candidate regardless of ownership. Fixing only the list endpoint while leaving direct fetch open would be an inconsistent, incomplete implementation of the same rule. Using 404, uniformly, for both "doesn't exist" and "exists but you can't see it" — this is the same existence-oracle reasoning already applied in Step 6.1's path allowlist: revealing "yes, this exists, you're just forbidden" via a 403 would leak the candidate's existence to a project with no right to know about it.
