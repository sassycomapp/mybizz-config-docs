Working through why, most likely cause first:

Most likely: role membership, not a revoke failure. If memory_governor_svc is a member of a role (like PUBLIC, or possibly inherited some other way) that independently has CONNECT on gbrain, an explicit REVOKE ... FROM memory_governor_svc doesn't override that — PostgreSQL's revoke only removes what was granted to that specific role, not inherited grants from group membership. Since REVOKE CONNECT ... FROM memory_governor_svc targets the role directly, and it still connects, the access is very likely coming through PUBLIC's default CONNECT privilege in a way the ordering of my commands didn't actually clear — or the gbrain database itself has datallowconn open in a way that doesn't route through the DACL I revoked.

That \l gbrain output confirms the exact mechanism. Reading the ACL string =Tc/postgres — the role name before = is empty, which in Postgres ACL notation means PUBLIC. So PUBLIC holds T (temp) and c (connect) on gbrain, granted by postgres. This is Postgres's default: every database grants CONNECT to PUBLIC automatically at creation, unless explicitly revoked.

That's the whole bug. Revoking from memory_governor_svc by name did nothing, because the actual privilege letting the connection through belongs to PUBLIC, and every role — including a brand-new one you just created — is implicitly a member of PUBLIC. You can't override an inherited PUBLIC grant by revoking from one named role; you have to revoke it from PUBLIC itself.

(You sent only the third check, not the first two — that's fine, this single output already fully explains it, no need to send the others.)

One thing to flag before running the fix, not proceeding on assumption: revoking PUBLIC's CONNECT on gbrain affects every role on this instance, not just memory_governor_svc. Looking at the ACL again — postgres=CTc/postgres — the postgres role already has an explicit grant independent of PUBLIC, so it's unaffected. Per gbrain-config.md, GBrain's own connection string uses the postgres role itself, so this should be safe for GBrain's operation. But you know this environment better than I can verify from documents alone — if any other role besides postgres and memory_governor_svc is meant to connect to gbrain, this revoke would break it. If you're not aware of one, this is also just standard Postgres security hardening (revoking PUBLIC CONNECT on non-shared databases is common practice), so it's a reasonable fix either way.
