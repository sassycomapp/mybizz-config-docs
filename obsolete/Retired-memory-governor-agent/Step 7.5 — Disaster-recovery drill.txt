Add it now, not defer — and the reasoning is worth being precise about, because "low-risk to regress" isn't actually the right test for whether something needs a permanent test.

Best practice: the value of a regression test tracks how catastrophic silent failure would be, not how likely failure is. This is literally the disaster-recovery mechanism — the one piece of this whole system whose entire job is to work correctly at the exact moment everything else has already gone wrong. If a future refactor to models.py — adding a field, changing a default, renaming something — silently broke JSON round-tripping, nothing in the day-to-day system would ever surface it, because Postgres is the primary path every other test already exercises constantly. The gap would sit invisible until the actual disaster arrived, which is precisely the worst possible moment to discover it. That asymmetry — cheap to test now, catastrophic to discover late — is the standard justification for testing recovery paths permanently even when the underlying mechanism looks simple, and it's exactly the same reasoning that already justified Steps 7.3 and 7.4 getting real tests.

Second reason, specific to this codebase: commit_and_push_register_changes()'s two fixture bugs earlier tonight were caught immediately because Step 7.4 had a permanent test to run repeatedly, not just a one-off live proof. A one-off proof in this specific conversation is real evidence today; it says nothing about whether the mechanism still holds after the next change.

Writing it now, following the same pattern already proven for test_registers.py — genuine round-trip, no mocks, no shortcuts.
