Step 7.1 — registers.py

Pulled the real register schema directly from Architecture §8.2 rather than guess — nine columns: doc-id/filename/folder/type/state/date-registered/date-state-changed/superseded-by/notes. This schema was designed for tracking documents living elsewhere on disk, and a GovernedMemoryCandidate doesn't quite fit that shape natively, so mapping it required a few real decisions — flagging them rather than silently picking:

Column mapping. doc-id → memory_id, filename → candidates/<memory_id>.json, type → memory_type, state → status, notes → owning_project + writer_identity (for quick human scanning without opening the JSON). date-registered is set once, on first write; date-state-changed updates every time the row is touched again.
superseded-by is written on the old candidate's row, not the new one. When candidate B supersedes candidate A, A's register row gets superseded-by = B's memory_id — never deleted, matching this project's standing "never delete, only retire" rule already established for documentation elsewhere.
This module writes files only — it does not commit or push to git. That stays the worker's responsibility (Step 7.2), keeping registers.py narrowly scoped to file mechanics, consistent with every other module's single-responsibility boundary in this codebase.
One honest gap: I don't have the literal register-global.md/register-local.md markdown table formatting convention already established elsewhere in this environment in front of me this session. I've used a standard markdown table as a reasonable default — flagging this explicitly so it can be corrected to match the exact existing convention if it differs, rather than silently assuming mine is right.
